# Decisions

Every settled decision, with a one-line reason. A new decision gets the next number; a changed decision is struck through and replaced by a new entry that names it. Undecided questions are tracked as GitHub issues, never here.

## IPTC standards

| #   | Decision | Reason |
| --- | -------- | ------ |
| D40 | **Digital source type.** A publication is `trainedAlgorithmicMedia`; once the audit log shows an editor changed its text it becomes `compositeSynthetic` (label: "AI-made, edited by a person"). Replaces D26. | IPTC defines `compositeWithTrainedAlgorithmicMedia` as human media edited with generative AI, the reverse of ANR's case; `compositeSynthetic` is a mix of elements with at least one AI-made. |
| D41 | **Subjects are IPTC Media Topics.** Each beat in `policy.yaml` lists one or more Media Topics; the summariser places a lead in beats, and a publication carries its beat's topics. | Standard subject codes come from configuration, so no model invents a code. |
| D42 | **Genre per format.** `format.yaml` names one IPTC genre (newsletter issue `genre:Summary`, classic article and podcast episode `genre:Feature`, artist story `genre:Profile`); an opinion item adds `genre:Opinion`. | Readers and machines can tell a briefing from a profile from opinion. |
| D43 | **ninjs 3.2 out.** Every published publication has a ninjs 3.2 twin at its page URL plus `.json`, with subjects, genres, digital source type and trust indicators. Leads keep the fields of a ninjs item. | IPTC's JSON news format is the syndication format; leads are exportable the same way. |
| D44 | **Reader pages carry schema.org JSON-LD** (`NewsArticle` or `PodcastEpisode`, `digitalSourceType`, `about`, `genre`, `inLanguage`; publisher a `NewsMediaOrganization` with its policy links). No HTML meta tag for the source type. | schema.org's `digitalSourceType` takes IPTC's values; no standard meta tag exists. |
| D45 | **Images use IPTC Photo Metadata.** Ingestion reads creator, credit line, copyright notice, web statement of rights, licensor and digital source type from XMP; the publisher writes them back into every published image, next to its C2PA manifest. An image keeps its own recorded source type, never the publication's, and an unknown one stays unset. | Credit and licence travel with the file. |
| D46 | **Vocabularies are vendored** in `packages/schemas/iptc/` (NewsCodes under CC BY 4.0, and the ninjs 3.2 JSON Schema), refreshed by hand; config validation rejects unknown and retired codes. Reader-facing names in fa, en and tr are ANR's own. | CI stays offline and reproducible; IPTC labels exist only in English. |

## Ingestion

| #   | Decision | Reason |
| --- | -------- | ------ |
| D55 | **Raw pages** are stored content-addressed (`raw/<sha256>`): in a local directory while ANR runs on the laptop, in R2 from milestone 7 (`ANR_RAW_BUCKET`). A lead keeps the key of the page as fetched. | The same bytes are stored once, and a key always names one frozen snapshot. |
| D56 | **Near-duplicates** are found in two stages: leads of the last 30 days whose 64-bit SimHash of word 3-shingles is within 12 bits, then confirmed when the Jaccard overlap of their shingles is at least 0.8. Texts under 24 shingles get no SimHash. | SimHash alone is noisy on short posts (a one-line intro moved a copy 8 bits; unrelated texts sit near 32); the exact overlap decides. No extra index service. |
| D57 | **Lead sightings.** Every URL a lead was seen at is a row (`lead_sightings`: original, same URI, same text, near-duplicate), with its source. A copy never becomes a second lead. | Source independence is counted from one lead and its sightings, so syndication never looks like corroboration. |
| D58 | **Fetching.** One client for every request: http and https only; the host resolved at connect time, every answer required public, and the connection made to a checked address (IPv4 first, then each in turn); each redirect hop checked again (at most 5); address literals refused before any transport; robots.txt per origin (RFC 9309: 4xx no rules, 5xx or unreachable nothing, asked again after 5 minutes), its `Crawl-delay` the host's minimum gap; otherwise 1 s between requests to a host (3 s for arXiv's API); 10 MB per response; pages decoded in their declared charset; at most 50 new leads per scheduled run. A listing's ETag and Last-Modified are kept only when every item was handled (none left by the cap or a failed fetch other than 4xx), so the next run takes the rest. An answer that cannot be read counts as a failed fetch of the source. The `ingest-source` job expires 5 minutes after its 15-minute HTTP call times out, so one source never has two runs at once. | Ingestion is the only part of ANR that touches the web; an injected URL can reach neither a private network nor a site's disallowed pages. |
| D59 | **Paper tier rules.** An arXiv paper is flagged and not stored when withdrawn; low (tier 3) when its abstract is under 200 characters or it is only cross-listed into the source's categories; high (tier 1) only when Semantic Scholar shows a venue on `papers.high_venues` or at least `papers.high_citations` citations; otherwise medium (tier 2). Each arXiv run re-checks its papers of the last 30 days and only raises tiers, and only once the Semantic Scholar source has `terms_checked`. | A paper earns tier 1 from independent evidence of review or impact, never from its authors' own comment. |
| D60 | **Hacker News** items are stored as metadata only: the lead is the discussion page (title, text, points), and the linked article is a ninjs link that is never fetched by the scheduled run. | Linked sites are arbitrary and their terms unread (D17); an agent can still request a page, at tier 3. |
| D61 | **Source requests** run the same pipeline at once and return the lead. A URL takes a source's tier only inside that source's section (its host and first path segment, from the source URL or a lead it gave), and only if the source's terms are checked; elsewhere on a site with an unchecked source it is refused; anything else is tier 3, and so is a vouched URL that redirects out of its section. At most 5 fetches per agent run, logged in `source_requests` before each fetch, whatever the fetch turns out to be. | An injected page cannot promote itself, not even on a shared host such as `huggingface.co`, and a run cannot turn into a crawl. |
| D62 | **Ingestion contract.** The agents worker calls the ingestion service over internal HTTP with bodies defined as JSON Schemas in `packages/schemas` (`ingest-run`, `ingest-result`, `source-request`, `source-request-result`). 404 and 422 (unknown, or never to be fetched) end the job; 502 and other failures are retried by pg-boss. | One definition for both languages; a refusal needs a person, a failure needs only time. |
| D63 | **Summariser.** One run per new lead: an Agent run row and its `agent-run` job are written in one transaction. The model answers in plain JSON; code validates it (summary of at most 400 characters in the lead's language, beats only from the newsroom's live slugs), with one retry carrying the errors, then outcome `invalid`. A valid answer is stored with the run's outcome and tokens in one transaction; a finished run is never rerun, and a lead has at most one summariser run (a unique index). Without a model key the worker does not take summariser jobs, so they wait; at start and after each ingest run it re-queues runs that have no job and leads with no run, and closes as `error` a run whose job used up its retries. At most 20,000 characters of the lead are sent. Cost stays empty until milestone 3's budgets. | Code, not the model, decides what counts as a beat, and no provider-specific structured-output feature is needed. |
| D64 | **API sources and robots.txt.** An `api` source's own requests (its listing URL, and per-item calls such as Hacker News items) follow the API's terms of use, read before `terms_checked`, and its rate limits; robots.txt is not consulted for them. Every page fetch still honours robots.txt. Amends D58. | robots.txt (RFC 9309) speaks to crawlers; an API is an explicit invitation with its own terms. arXiv's API host disallows every crawler while its API documentation directs programs to it. |
| D65 | **Beat descriptions.** Each beat in `policy.yaml` may carry a one-line `description` (stored on the beat); the summariser sees it next to the slug and the beat's Media Topic labels. | Beats of one newsroom often share their Media Topics (every AI beat is "artificial intelligence"), so labels alone cannot tell them apart. |
| D66 | **Model call pacing.** The agents worker spaces summariser calls by `ANR_SUMMARISER_RPM` (default 10 a minute). A rate-limit answer (429) never uses a pg-boss retry: the job is queued again after the provider's suggested delay, or an hour for a daily quota, and every other call waits meanwhile. LangChain's own retries are off. | Provider limits depend on the API key's tier, so the rate is a deployment setting; a free-tier key stays within its quota without losing summaries. |
| D67 | **A copy from a better source credits the lead.** When a source with a better tier sees a stored lead (same URI, same text or near-duplicate), the lead takes that tier and source; its text stays frozen and every sighting is kept. arXiv papers are never raised by a copy: their tier follows D59. | Which source happens to run first must not decide a lead's tier. |
| D68 | **Age limit.** A newsroom's `policy.leads.max_age_days` bounds scheduled runs: an item older than that by its newest date (published or updated) is not stored, checked before its page is fetched when the listing dates it and after extraction otherwise; an undated item is not stored. An agent's request has no age limit. The AI newsroom uses 14 days. | A source's first run must not backfill years of posts into the pool, or spend a summary on each. |
| D69 | **Listing pages keep articles only.** A link from a `site` listing is stored only if its page says it is an article: `og:type` article, or JSON-LD of an Article type (Article, NewsArticle, BlogPosting and their kinds). Feed items and agents' requests are not filtered: a feed lists items, and an agent asks for a page on purpose. | A listing links its category and tag pages too, and the path alone cannot tell them from posts. |
| D70 | **Feed-only sources.** A source with `pages: false` stores each feed item's own title and text as the lead and never fetches the item's page. | For terms that allow a publisher's feed but ban robots on its site. |
| D71 | **Fact-checker model family.** Every catalog model has a `family` (the weights, whoever serves them). The fact-checker's chain drops every family in the story's desk Agent runs and tries the rest in order; config validation requires at least two families in it. Replaces D22. | The same weights served by two providers are the same writer; a run that fell back may have used several. |
| D72 | **Model chains and free development models.** Each role names an ordered chain of catalog models; `@anr/models` calls it and falls through on rate limits, outages and retired models, never on a bad key or request, and holds the run when the chain is exhausted. `ANR_MODELS=free` selects `config/models.free.yaml` (Gemini, Groq, OpenRouter, Mistral, NVIDIA NIM free tiers) for development; deploy refuses it. | Development costs nothing while no single free tier is enough; free tiers may train on prompts and promise nothing. |

## Desk and gate

| #   | Decision | Reason |
| --- | -------- | ------ |
| D73 | **Agent tools.** `read_lead` returns a lead's frozen text (cut at 12,000 characters), publisher, tier, beats and any withdrawn mark; `search_leads` ranks the newsroom's leads by `pg_trgm` word similarity of the query to `anr.normalize_text()` of headline, summary and text (a GIN index on that expression), then tier and recency, never returning withdrawn leads; `request_source` calls ingestion's `/request-source` (D61) and answers every refusal as text. Models are bound to these three; code calls `submit` with a validated draft. A test pins the four names. | Word similarity, not similarity, because a query is short and a lead long; a model passing a whole draft as tool arguments is the least reliable thing free models do. |
| D74 | **Corroboration.** A claim may list up to four further sources, `also: [{lead_id, quoted_passage}]`, stored in `claim_sources`. Each passage is quote-matched like the first; independence counts the publishers (source publisher, else the URL's host) of the claim's sources whose passage matched. | A claim has one lead, and a syndicated copy is never a second source (D57), so a non-tier-1 fact had no way to show two. |
| D75 | **Prompt assembly.** Platform role prompt, the newsroom `style.md`'s "All languages" section and the target language's section, and the format `guide.md` (a newsroom may override the guide). At most 5 KB in UTF-8 bytes, including the desk's step prompts; `prompt_version` is the role and a hash of the assembled text. A test covers every newsroom, series format and language. | Persian is two bytes a letter; a content hash versions every part at once. |
| D76 | **Budgets.** `format.yaml` `run_tokens` caps input plus output tokens over a run's model calls; the run ends there and its publications are held. `policy.yaml` `budget: {monthly_usd, check_reserve_usd}` caps spend per calendar month in the newsroom's timezone over every Agent run (summaries included; the summariser records its cost from now on, D63), counting what interrupted attempts spent: writing roles (planner, desk, renderer, summariser) do not start at `monthly_usd - check_reserve_usd`, the fact-checker and item matcher not at `monthly_usd`; a run that started may finish. A `notices` row tells the Editor-in-Chief at 80% and at the writing limit, once a month each. A desk or renderer run that cannot start is `paused` and its publications held. | The reserve is money only checks can spend, so a draft written before the cap is still checked; the token cap bounds what a started run can add. |
| D77 | **Desk and renderer.** The desk graph is read (code: the assignment's leads, most credible first, each with its summary and the first 1,500 characters of its text) → outline → draft → claims → validate, research tools bound at every model step (six tool rounds a step). Validation is the format's zod schema plus what it cannot express: claims cite only leads given or read in the run, none withdrawn, each passage found after normalisation and at least 20 characters, the story's beat live and not banned, every item listing known claims. One retry with the errors; a second failure holds every publication of the assignment. Claims are written in their lead's language, the story in the newsroom's primary language; a renderer run per other series language writes the same items with the same claim ids and no tools. A submit closes the run, stores story, claims (`ref` c1, c2…), sources and rendition, marks the publication drafted and queues the renderers, then the gate, in one transaction. | Same-language claim and passage make fact-checking a comparison, not a translation; the gate needs every language, and other formats and podcast scripts wait for milestone 5's renderer. |
| D78 | **Withdrawn leads** (issue #3). A stored lead later found withdrawn keeps its frozen text and gets `withdrawn_at` and a reason: search and assignments skip it, the desk cannot cite it, and the verifier fails a claim that does. Each arXiv run asks arXiv for its record of the source's papers of the last 30 days (`id_list`, 50 a request) and marks those it now calls withdrawn, as does a listing that shows a stored paper withdrawn. Retraction data and a venue deny list are not part of this (issue #3). | Claims may already cite the lead, so it can neither change nor disappear; lowering its tier would let it keep corroborating. |
| D79 | **Verifier code checks** run in the Python verifier service (`POST /verify`, JSON Schemas `verify-request` and `verify-result`), which reads the story with `with_newsroom` and stores every result as a Check in one transaction: rendition schema; quote match (shared normaliser, then whitespace collapsed, at least 20 characters); withdrawn leads; source independence; opinion where policy forbids it; beats (the story's and every cited lead's: banned or not yet placed fails, restricted is listed); item–claim consistency (every item lists known claims; its numbers, after folding Persian and Arabic digits and separators, and its Latin-script names are in its claims' text or passages); outside-article leads exist; style lint per language (Arabic ye and kaf and a detached می in Persian, a Persian rendition mostly in Persian script, no Arabic script in Latin-script languages, English hype words, double spaces); and `checks.yaml` rules by id, their numbers read from the rule text. An unknown rule id is an error. The disclosure check renders each rendition through every channel template its series uses for that language with `@anr/render`, the publisher's own renderer, and requires the label. | A story-wide result is stored once per rendition so each publication shows it; the disclosure check must see exactly what would be sent. |
| D80 | **Gate and policy.** A `gate` job per story is queued when its last language is written (by the desk itself for a one-language series), on a `stately` queue keyed by story, so one gate per story runs at a time: code checks, disclosure, then, only if every code check passed, the fact-checker (one fresh call per fact claim and passage, each check recording which source it covers, its chain without any family of the story's desk and renderer runs) and the item matcher (one call per item with its claims), storing each answer as it comes; a call no model answers is an error or timed-out check. Policy then re-reads each publication under a row lock, leaves any that is no longer drafted, and passes one only when every check it needs exists and passed; it goes on to `scheduled` only as daily news in an `auto_publish` format with no restricted beat; anything else is held (`with-editor`) with policy Checks naming why. The agents worker holds every publication still assigned or drafted 30 minutes before its slot. | A check that never ran leaves no failure behind; requiring each expected check makes silence a hold, never an approval. |
| D81 | **Daily assignment.** At a daily series' `assignment_at`, its slot is that day's cadence time in the newsroom's timezone (a passed slot is skipped); its leads are those stored in the last 24 hours, summarised, not withdrawn, in no banned beat and not used by the series before, ordered by tier then date, at most two per item the series allows (24 at most). One transaction writes the assignment, its leads, one publication per series language and the desk run with its job; no leads writes a `no-leads` notice instead. | A summary means the lead's beats are known, so a banned one is never assigned. |
| D82 | **Prices.** Every model a role or TTS uses needs a `price` in its models file; config validation rejects one without. Paid prices come from the provider's published price list, cited in the file. | A budget cannot count what it cannot price. |
| D83 | **Too large for one model.** A 413 (a request over a model's own limit, such as a free tier's tokens per minute) moves the call to the next model in the chain with no cooldown; it is not a bad request. Amends D72. | A desk prompt that one free tier refuses fits another, and smaller calls still fit the first. |
| D84 | **Local models in development.** A models file may name an OpenAI-compatible server on this machine (plain `http` to `127.0.0.1` or `localhost`, no key, its own `timeout_s`); config validation keeps such a provider out of `models.yaml`. The free profile tries LM Studio first: `openai/gpt-oss-20b` writes (desk, renderer), `google/gemma-4-12b` checks (fact-checker, item matcher), both with a 64k context, sized for a 36 GB laptop. A 400 over a model's context window counts as too large (D83), and "model unloaded" as an outage. | Free cloud tiers were overloaded or too small for the desk's prompt; a laptop's own models have no rate limits and keep prompts local. Gemma 4 12B could not produce the desk's claims step (it repeated its draft twice); one claim or item at a time against one passage suits it. |
| D85 | **Output cap and reasoning effort.** One model call may write at most 8,192 tokens, thinking included. A model in a models file may set `reasoning_effort` (`none`, `low`, `medium`, `high`), sent as is to an OpenAI-compatible provider; the free profile turns local Gemma's thinking off. | With thinking on, Gemma 4 12B spent 13–18k tokens reasoning per desk call and answered in 3, so every call hit its 10-minute timeout. The cap stops a looping model in minutes; the effort setting keeps the tokens for the answer. |
| D86 | **Hyphens fold; answers are read leniently in shape, never in content.** Text normalisation (SQL, Python, TypeScript) maps the hyphen, non-breaking hyphen and minus sign to `-`. A desk's or renderer's draft with brackets left open at its very end is closed, and a rendition written inside the story is moved beside it; nothing else is repaired, every check still runs on the result, and a checker's verdict is never repaired (one that does not parse holds). A missing item `kind` is named as such. A model told to answer after its tool rounds is no longer offered the tools. | Models write `‑` where sources have `-`, so exact quotes failed to match. Models of two families nested the rendition and dropped the closing brace on every try, and at temperature 0 a retry repeats the slip; Qwen 3.8 27B kept calling tools after it was told to stop. A content hash changes only for text containing those three characters. |
| D87 | **Re-drafting a returned publication.** A desk or renderer submit for a publication that is `assigned` replaces its rendition links with the new story's; the earlier story, its claims, renditions and checks stay, and the audit log keeps every status change. A publication past `assigned` keeps its links, and a second draft for it fails rather than replace them. | A publication an editor returns to the desk (the lifecycle's `WithEditor --> Assigned`) must take a new draft; its links name what goes out now, while the history lives in the rows a re-draft never touches. |

## Publishing

| #   | Decision | Reason |
| --- | -------- | ------ |
| D88 | **Splitting.** `@anr/render` `renderParts()` gives what a channel is sent: the template's output cut at blank lines into messages of at most the channel's limit (Telegram 4,096, counted as visible UTF-16 text after tags and entities), never inside a block; the lines from the disclosure label onwards end every part. A missing label, a block or footer that cannot fit, or a part whose tags do not balance is an error. The gate's disclosure check uses the same parts. | A split inside a tag is refused by Telegram; a label only on the last message leaves the others unlabelled; the gate must check what is sent (D79). |
| D89 | **Send protocol.** Each attempt renders every channel and requires the label on every part; the first writes a `pending` Post per part with its text, then for each part in order commits `attempted_at` (only while the publication is still scheduled) before the call and `sent` with the message id after. A retry sends the stored text; if the text has changed (an editor's edit after a hold), parts not yet tried are replaced, and once a part was sent the publication is held instead. A part still pending with `attempted_at` set, or a send whose answer is lost (timeout, reset, 5xx), is `unknown` and holds the publication; it is never re-sent. A refusal is `failed`: a rate limit or an unreachable channel keeps the slot for the next sweep until an hour past it, anything else holds. One session advisory lock per publication keeps overlapping sweeps apart. The site goes live (`published`) only after every other channel's parts were sent. | The Bot API has no idempotency key, so the Post row is the only record of a send; stored text keeps part numbers meaning the same message. |
| D90 | **Restores.** The restore scripts add a row to `restores`. | D91 | **Missing channels.** A series' channel kind and language with no active channel row is skipped, with one `no-channel` notice to the Editor-in-Chief; the site needs no row, and an active `site` row records a Post with the page URL. | A newsroom publishes to its site before it sets up Telegram; holding every issue for it would stop daily news. |
| D92 | **Publication pages.** A publication's page is `/<series>/<slot date in the newsroom's timezone>` under its language's prefix, stored as `path` with its `title`, `search_text` and `edited` when it is published; the label and the IPTC source type both read `edited`. | One stored URL for Telegram links, the site, ninjs and search; one flag keeps the visible and machine-readable disclosure the same. |
| D93 | **The publisher's sweep** runs every minute under the app role: it lists newsrooms and works inside `withNewsroom()` for each, like the gate's deadline sweep. Amends the technical design, which named the system role. | Row-level security stays on for the code that sends; only config sync needs to bypass it. |
| D94 | **Review sample.** When the publisher publishes a publication no person approved, it adds it to `sample_reviews` with probability 0.1. An editor marks each one fine or a miss; a miss needs a note saying what the gate should have caught, and the open misses are what new checks and policy rules are made from. | The charter's 10% audit, with each miss kept as evidence rather than a passing remark. |
| D95 | **Desk sign-in.** The API verifies the Cloudflare Access JWT on every desk request (`jose`: the team's signing keys, issuer, the application's audience tag, RS256) and maps its email to a user, then to a membership in the newsroom named in the path; channels are the Editor-in-Chief's. The web desk forwards the JWT and calls the API. The first membership is the operator's (`pnpm --filter @anr/api desk:grant`). `ANR_DESK_DEV_EMAIL` signs in without Access only on `localhost` with both `CF_ACCESS_*` empty; deploy refuses it. | One check, in one place, that a dev setting cannot open in production. |
| D96 | **Returning to the desk.** An editor's return moves every held publication of the assignment back to `assigned`, records the note in the audit log and queues a `redraft` job in one transaction; the agents worker starts a new desk run on the same leads (D87). The deadline sweep gives a returned publication an hour from its return, even past its slot. | The API never picks models; without the grace a return after the slot would be held again before the desk could write. |
| D97 | **Editing text.** An editor may change the text of a held publication's first rendition: every string field except `kind`, `claim_ids`, `lead_id`, `id` and `language` (`textFields` in `@anr/core`), and the result must still match the format's schema. The edit is audited as `edit` on the rendition, which turns the label into "edited by a person" and the IPTC type into `compositeSynthetic`. No edit once a part was sent or may have been (in flight included), `host` and `speaker` stay fixed, and checks are not re-run: approving the edit is the person's call. | Editors fix wording without a re-draft; structure stays tied to claims and leads, and the disclosure follows the audit log, not a flag someone sets. |
| D98 | **Deciding with a preview.** Approve and return are only on a publication's own page, which shows what would be sent now: each channel's parts and the site page, from the publisher's own template context (`@anr/render`), renderer and label check. A test holds the preview equal to the parts the publisher sends. Approve and edit carry the version the page showed and are refused if the publication changed since; with no preview there is no approve button. | An approval covers exactly the bytes that go out; a queue-wide button would approve unseen text. |
| D99 | **Measures.** By week in the newsroom's timezone: hold rate is publications in the week's slots past the gate with a check that did not pass, an editor's pull-back excluded; sample misses by sampling time; corrections per 100 published; cost per publication is all agent-run spend over publications published (summaries cannot be tied to one piece); audience is page views and downloads per language and each Telegram channel's latest count. Editor minutes: opening a held publication is audited as `open` (once per person per 10 minutes), and each approve or return (once per return, though it moves every language) counts back to the same person's first open of it within the hour before. | Each measure from data ANR already keeps, with a definition that can be checked; the hour cap stops a forgotten tab counting as work. |
| D100 | **Pull-back.** An editor may take a scheduled publication back before it goes out: it returns to the review queue with a `pulled-back` policy check carrying the note, audited as `pull-back`. Mid-send, the publisher stops before the next part; approving again sends the rest. | The upcoming week can be stopped without waiting for something to fail; the reason stays with the piece. |
| D101 | **Channel checks and tokens.** The Editor-in-Chief may test a channel or replace its credentials. A test is a `channel-check` job for the publisher, which asks the channel without sending (Telegram: `getMe`, `getChat`, `getChatMember`) and stores the answer on the channel row. New credentials are sealed to the same newsroom and channel, replace the old ones, are audited redacted, and queue a check. | Only the publisher talks to channels; a revoked token is fixed without deleting the channel and its posts. |
| D102 | **Filing a miss.** A sample miss is filed as an issue in the platform's repository (`ANR_ISSUES_URL`): the desk opens a prefilled new-issue page in the editor's browser and records the issue's URL on the sample. The issue carries the note and where the publication is, nothing else, since the repository is public. | Checks are code and policy rules are config; both change through the repository, so the miss starts there, with no server-side token. |

## Planning and podcasts

| #   | Decision | Reason |
| --- | -------- | ------ |
| D103 | **Planning tick.** A `plan` job runs at 06:00 in each newsroom's timezone (a missed day runs once on waking). It starts a planner run for the themes of the cycle that begins within 7 days, or of the current cycle if it has no proposals yet. It also starts one for three candidates of each weekly series whose pick window is open (from `pick.by` to the end of `editor_picks_by`), once the slot's cycle has an approved theme. Without one, a `no-theme` notice is sent once per cycle. Each run has a task key: a running or submitted run is never started twice; a failed one sends a `plan-failed` notice and is tried again the next day. Proposals are in English, for the Editor-in-Chief, and every theme and candidate lists stored leads, none withdrawn or in a banned beat. A theme's calendar gives a focus for each Monday-week the cycle touches; the week of a pick's slot looks it up. | Cycles of `10d` or `2w` from a date cannot be a cron; a daily, idempotent tick handles any length and a laptop that slept. One Editor-in-Chief reads both newsrooms' proposals; the desk writes the pieces in their own languages. |
| D104 | **Pick deadlines.** The planner's submit stores the candidates and, in the same transaction, a `pick-deadline` job that starts at the deadline (the end of the `editor_picks_by` day). Unchosen by then, the pick is skipped, audited, and a `pick-missed` notice is sent. No assignment is made, so the slot and any episode segment built from it are left empty. A choice made in time queues an `assign` job, which makes the slot's assignment from the chosen candidate's angle and leads (minus any since withdrawn or banned) in the pick's cycle, so the gate treats it as themed. A series with a pick has no `assignment_at`; a weekly series built from segments has one, as a weekday and time. | A graph never waits for a person (invariant 10); a deadline that is a row and a job survives restarts and needs no polling. |
| D105 | **Planning at the desk.** The Editor-in-Chief, not an editor, approves one proposed theme per cycle, with its theme, angle and each week's focus edited as wanted (the weeks are fixed). Approving declines the cycle's other proposals. They also choose one of a pick's three candidates; a choice after the deadline is refused. Every decision and edit is audited. | The charter gives the agenda to the Editor-in-Chief; an edit of a proposal is the Editor-in-Chief's direction, not a change to published text, so it does not touch disclosure. |
| D106 | **TTS spend.** Every episode's TTS calls are one Agent run row with role `tts` (code's, not an agent role), its tokens and cost priced from the models file, counted toward the monthly budget. Voicing stops at the writing limit, like the desk. | A budget counts every model call (D76), and TTS is the largest one an episode makes. |
| D107 | **Episode stories and scripts.** At a weekly segment series' `assignment_at` (as a weekday and time), code finds the stories each segment retells, published in the 7 days before the slot: every story of a news recap's source series, and the latest one for a story segment. The episode gets its own story; its claims are copies of theirs (same lead, passage and further sources, `copied_from` the original), so the gate checks it like any story, re-checking facts at little cost. A segment with nothing to retell is left out, and the verifier then holds the episode. One renderer run per language writes the script from the claims and that language's published texts. It makes one call per part (a recap's source story, the story's plan, each of its six beats), each in a short conversation with one retry, and code assembles and validates the whole. Topics and beats list the claims their lines rely on, so the gate checks a beat, not each line. Code opens every episode with the AI-voice intro from `_partials/ai-voices.liquid`; the gate checks that each host and the narrator say they are AI (`ai-voices`), and the script never repeats it. | One call per part stays far under the 8,192-token output cap (D85) in every language. Copied claims keep the gate's one-story model. Line-level items would mean hundreds of item-matcher calls per episode. An intro the model wrote could be edited away (D97); one rendered by code cannot. |
| D108 | **Sound cues** are synthesised by ffmpeg from sine-tone formulas (`apps/publisher/scripts/cues.ts`) into `config/newsrooms/<newsroom>/audio/<series>/`: a sting, a transition, a bed swell, a bed out, a loopable bed and a jingle, in each series' own key, with a `LICENSE.md` saying they are owned. Config validation requires every file and the licence for each podcast series. | Owned without question, reproducible, and a new newsroom adds its cues as configuration. |
| D109 | **Episode audio.** Once an episode's script is approved (scheduled), a `podcast-audio` job voices each line with Gemini TTS: the speaker's voice, and the line's direction as a style prompt. Lines are cached by model, voice, language, direction and text. The job then joins the clips with the series' cues and loops the bed under story segments, ducked under speech. It normalises loudness in two passes to −16 LUFS (true peak −1.5 dBTP), and encodes 44.1 kHz mono MP3 with ID3v2.3 tags and a chapter per topic and story. It then signs with c2patool's test certificate (after tagging, since signing hashes the file), reads the manifest back, stores the file and writes an Episode row for that script version. Files go to a local directory (`ANR_MEDIA_DIR`) until milestone 7 moves them to R2. A failure holds the publication with the reason. An approval of an episode covers its script; the audio made from it after approval is checked by code, not seen by the editor first. Amends D98. | The editor approves the words; voicing, mixing and signing have one right answer each, and a cached retry costs nothing. |
| D110 | **Podcast feed and downloads.** A `podcast-rss` channel per language is sent to by storing the episode's rendered `<item>` as its Post; the site serves `/podcast/<series>.xml` under each language from those Posts of published episodes, with the AI label in the channel description. An episode is published only once audio made after its last approval exists; until an hour past its slot the publisher waits, then holds. Its audio is at `/a/<publication>.mp3` on the site, which counts a download and serves the stored file (a redirect to object storage from milestone 7). A listener is counted once per episode and day: the key is an HMAC of address and user agent under a secret derived from the platform key for that day, and keys older than yesterday are deleted. Crawlers are not counted. | The feed carries exactly what was sent (D89); per-language audience without storing who listened (D27). |
| D111 | **Host names per language.** A podcast series may give `host_names` per language: each host's name as spoken and written there. The AI-voice intro, its gate check, the show notes and the script writer's prompt all use these names; lines still name their speaker by key. | A Latin key such as `niloofar` read inside Persian speech is wrong and unreadable in Persian notes. |
| D112 | **TTS requests per segment.** A TTS adapter says how episodes are voiced: `line` (one request per line, as local engines will be) or `segment`. Gemini TTS is `segment`: a segment's consecutive lines go into as few requests as possible, at most two voices and about 1,200 words each, a new request at each sound cue; each line is its own text part tagged with its speaker, and a cached request is never sent again. A segment's topics then share one chapter. Amends D109. | The account allows a few TTS requests a day: a 30-minute episode drops from about 150 requests to a handful, at the cost of topic-level chapters. |
| D113 | **TTS engines: enabled by the platform admin, chosen per newsroom.** Amends D109, which voiced every episode with Gemini. Local engines (Chatterbox, XTTS-v2, Dia) run as loopback servers (`tools/tts-eval/serve.py`), voice a line per request, and may be in `models.yaml`, since the laptop is the server. A series may set voices per engine (`engine_voices`); without them a local engine gives each speaker its own default. | The engine is a running choice of the people who run the platform and each newsroom, like channels; what can exist, and at what price, stays reviewed configuration. |

## Safeguards

| #   | Decision | Reason |
| --- | -------- | ------ |
| D114 | **Reader challenges.** Every published piece ends with a challenge form: what is wrong (20–4,000 characters) and, optionally, where the right information is. The site passes it server-side to the API's one public write, `POST /reader/newsrooms/{newsroom}/publications/{publication}/challenges`. Nothing about the reader is stored: the reader keeps a status link (not indexed, sent with no referrer) whose token is stored as its hash, and the rate key is an HMAC of the reader's network (address, or its /64 for IPv6) under a random secret kept in memory for the UTC day and then dropped, so no one can link a key to an address later. Per UTC day: 5 a reader per newsroom, 20 per piece, 200 per newsroom, counted under a lock; a filled hidden field drops a bot's. The challenge records the newsroom's `corrections_owner` as its owner and is due for acknowledgement in 24 hours and an answer in 48; in the same transaction it queues four `challenge-deadline` jobs, 6 hours before each deadline (`challenge-due` notice) and at it (`challenge-overdue`), each doing nothing once its step is done. Any member of the newsroom acknowledges (with an optional note) and answers (rejected or upheld); an answer acknowledges too. The status page shows the acknowledgement, the answer and the outcome. | The charter's 24- and 48-hour promise as rows and jobs, like pick deadlines (D104); an email address would be personal data ANR has no channel for in v1. |
| D115 | **Corrections.** Upholding a challenge names the claim that was wrong and gives a notice per language. The correction covers every published piece whose story holds that claim's original (followed up `copied_from`) or a copy of it: every language of the story and the episodes that retold it, each with its language's notice. Text and posts stay as they went out (D97); a `publish-correction` job for the publisher sets each notice's `published_at` and the piece's status to `corrected`, audited as the publisher. The site shows the notice on the piece and on the corrections page, the ninjs twin gets a new `version` and JSON-LD a `correction`. A piece holding the claim that is not out yet is held: a scheduled one is pulled back to an editor and a held one shows it, each with a `corrected-claim` policy check; one still being written meets the verifier's check (D116). Notices are not sent to Telegram or podcast feeds in v1. Measures count corrections by the week they were published, and checks an uphold adds later do not count as holds. | A wrong claim is wrong in every language and every retelling; only code publishes, and a person's notice is published like anything else. |
| D116 | **A correction's check.** Upholding stores a Check of kind `correction` (result `fail`) on the original claim, with the editor's lesson, what the gate should have caught; every correction of the challenge links it. The verifier's `corrected-claim` check fails any claim that is, or was copied from, such a claim, and episode stories do not copy it. The lesson is also filed as an issue, as for sample misses (D102), and its URL is kept on the challenge; the issue carries the lesson and where the piece is, never the reader's text. No model checks a correction. | The charter's "every correction becomes a new check": at once for the claim itself, and through the repository for the rule that would have caught it. |
| D117 | **Marked opinion.** In a newsroom with `opinion: allowed_marked`, an item that cites an opinion claim is marked `opinion: true` and a marked item cites only opinion claims (verifier `opinion-marking`); a format without the marker cannot carry opinion. Each marked item shows the label from `_partials/opinion.liquid`: config validation requires the partial in every template of a format whose items can be marked (and the disclosure partial in every template), and the gate's disclosure check requires the label as many times as there are marked items in every channel's output. The desk's role prompt allows opinion, a critic's or the piece's own judgement, only there and as a claim with the lead and passage it judges; elsewhere it still forbids it. The gate counts the label against the same output rendered without the marks, so the word in a sentence never counts. Episode stories do not copy opinion claims, since speech carries no label. | Opinion is labelled on every channel by code, never by the writer's goodwill, and the gate sees what is sent. |
| D118 | **Item shapes from the format.** The desk's outline and draft steps describe the items of the assignment's format, read from its `schema.json` (each kind of item with its fields, `opinion` where it can be marked), instead of the newsletter's. Prompt versions change with them. | Found by the Kültür gate: an artist story was asked for news items, so no new format could be written without code (invariant 9). |
| D119 | **Media items.** A member adds an image at the desk by URL: a Wikimedia Commons file page, or an image in a press kit with the kit's page, and the lead it goes with. An `ingest-media` job has ingestion fetch it through its one HTTP client (robots.txt for the file; the Commons API call is an API), store it in the raw store, and read IPTC Photo Metadata from its XMP packet (creator, credit line, copyright notice, web statement, licensor, digital source type, description; a malformed packet reads as empty); a failure is a `media-failed` notice, brought back unread when the same URL fails again. The same file added for another lead is another media item. Code records a Commons licence only for CC0, public domain, CC BY or CC BY-SA with an author, crediting "<author>, Wikimedia Commons" over any credit in the file's XMP, as the licence requires; a press kit's terms are recorded by a person, with a credit when the metadata has none. A recorded licence and the metadata it came with never change (a trigger). The desk agent sees each lead's licensed images and may set an item's `media_id`; it never writes a caption. The verifier's `media-licence` check, the gate's `media-credit` check and the publisher each refuse an image without a licence and a credit; config validation requires `_partials/media.liquid` in every template of a format whose items carry `media_id`. | Credit and licence come from records, not a model; images enter through ingestion like every other source material, and a person answers for every press-kit licence. |
| D120 | **Published images.** Before a publication with images is sent, the publisher writes each licensed image once: exiftool writes its Photo Metadata, the licence as usage terms and the web statement into a copy's XMP, then c2patool signs the copy with `c2pa.edited.metadata` (carrying the recorded source type, if any) and `c2pa.published`, giving the untouched source as parent ingredient. The copy is stored in the media store and served at `/m/<id>.<ext>`; its ninjs `associations` entry carries its own source type and licence. | Writing XMP changes the file, so a manifest the source already had would no longer validate; as the parent ingredient it stays valid inside ANR's. |
| D121 | **Ids are not item text.** `media_id` joins `lead_id` among the keys the verifier, the gate's item matcher and site search skip as reader-facing text. | Found by the Kültür gate: an image's UUID counted as numbers and names its claims did not contain, so every item showing an image failed `item-claims`. |
